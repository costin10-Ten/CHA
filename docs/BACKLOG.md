## 待辦

### 4. 三層驗證（取代目前單層的逐句驗證）

**來源**：使用者回饋（Phase 9 後的架構討論）

目前產出物只有一層確定性的逐句驗證。要改成三層，且人工層可回寫事實庫。

#### 第一層：自動驗證（已有）

`verification.ts` 的逐句綠黃紅：字元 bigram 覆蓋率 + 數字／否定／條件比對。
確定性、可重現、不呼叫模型。**維持現狀。**

#### 第二層：AI 驗證（新增）

對產出物再驗一次，四個面向與工作單 §4.1–4.4 的文章審核一致：

- **來源證據一致**：這句話與所引用的核定事實，適用情境是否相同
  （族群、劑量、暴露途徑、時間範圍有沒有被擴大或省略）
- **部會權責**：涉及主管機關時歸屬是否正確
- **科學正確性**：危害與風險、相關與因果、劑量與濃度是否混用
- **聳動表述**：**此階段放行度提高**——素材允許比事實庫活潑，
  只擋災難化、絕對化、把可能寫成一定，不擋一般的修辭

輸出：逐句判定 + 問題原句 + 理由 + 中性修正建議（不只給分數）。

**這一層不擋發布。** 它是看完整份產出之後給的建議性質文字，
供人工參考；能擋的只有第一層的確定性驗證與第三層的人工決定。

#### 第三層：人工驗證（部分已有，需擴充）

兩種改稿方式：

1. **逐句改稿** → 改完後**重產**
2. **整篇改稿** → 系統重新讀取改稿後的全文，**抓出變化處**，
   把每一處變化重新編成一句事實，寫進正式事實庫

人工確認的結果標記為「人工確認事實」，是**事實庫中權重最高**的一類。

#### 已定案的結構性決定

1. **人工改稿本身就是一份來源**：`source_type = 'human_edit'`，
   一併建 `source_versions` 與 `document_chunks`。
   這樣 `source_quote` 是改稿裡真實存在的句子，
   `promote_candidate_fact` 的既有防呆完全不用放寬。
2. **「最高權重」= 檢索排序權重 + 衝突浮現**。
   人工確認事實排序在前，但與其他事實衝突時要顯示出來，
   絕不靜默覆蓋。
3. **逐句改稿的「重產」= 重產該句所在的段落**，
   所有手改過的句子當作錨點鎖住不動。

#### 知識漂移的防範

人工事實沒有外部原文可回溯，長期會累積成「只有我們這樣講」。三項對策：

- 人工確認事實一律在介面上明顯標記
- 禁止二階衍生（人工事實不得再被抽成新的人工事實），切斷遞迴
- 提供篩選，可定期把人工事實拿回原始文件重新對照

### 5. 公開事實庫

**來源**：使用者需求（Phase 9 後）
「從正式事實庫裡拉出可公開資料，串接另一個智慧搜尋功能」

#### 核心判斷：發布是第二道關，不是正式事實的一個欄位

核定的意思是「這句話忠實反映原文」；公開的意思是
「我們願意把這句話掛在外面」。兩個不同的判斷。
而且 `source_quote` 是他人文字，內部審核可用，對外全文轉載是另一回事。

**不要在 `knowledge_facts` 上加 `is_public`**：修訂事實會建新版並把舊版標
`superseded`，布林欄位得跟著搬，等於「改一次就自動重新發布一次」，
而新版的對外文字根本沒人審過。

#### 結構草案

```
public_facts
  public_id          對外穩定識別碼，跨版本不變（下游索引的主鍵）
  knowledge_fact_id  目前對應的內部事實版本
  statement          發布當下的快照
  citation jsonb     標題／機關／網址／日期／授權，取代逐字引句
  quote_policy       full | excerpt | none
  published_at / withdrawn_at / needs_republish
public_fact_versions 發布歷程，撤下也留紀錄
```

#### RLS

不是關掉 RLS（§25 禁止），而是**只在這張表上明寫一條 `anon` select 政策**。
更乾淨的做法：基底表維持 owner-only，另開一個只含公開欄位的 view 給 anon，
連 `owner_id` 都不在對外投影裡。
配防呆測試：斷言除了這個 view 之外沒有任何 anon 政策。

#### 對外介面

- **增量 feed**：`GET /api/public/facts?since=<cursor>`，游標式分頁。
  **必須包含撤下的墓碑記錄**（`{public_id, withdrawn: true}`），
  否則下游永遠刪不掉東西。
- **全量快照**：JSONL，供下游冷啟重建。
- 向量：預設不發布（避免綁死我們的 embedding 版本），
  但可選擇附上 `embedding` + `embedding_model` 讓同模型的下游省成本。

#### 更新與撤下的傳播

內部事實被 supersede 時**不自動發布新版**，標成「待重新發布」、繼續供舊快照。
例外：修訂時明問人「這次修訂是更正錯誤嗎？」
若是，立刻撤下（feed 出墓碑）再排重新發布——繼續供錯的比暫時沒有更糟。
這個分岔由人回答，不用規則推。撤下一律是 `withdrawn_at`，不硬刪。

#### 發布時的警告（不硬擋）

`conditions` 為空的事實：沒有劑量／族群／暴露途徑的裸主張，
是最容易被斷章取義的形狀。

### 6. 搜尋系統民眾回饋

**來源**：使用者需求（Phase 9 後）
「不用即時，可能是匯回一個 word 檔，從那個 word 檔做一次 AI 驗證
（科學性，權責部會）選出待選事實（或待選修正事實）供審核」

#### 核心判斷：回饋能產生「待選修正事實」，不能直接產生「待選事實」

§25 禁止用模型自己的知識填答案。民眾回饋不是原文——沒有來源文件、
沒有可引用的段落。所以：

- **待選修正事實可以生成**：要修的那條正式事實有 `source_version_id`，
  修正後的引句**必須仍出自原本那段原文**。
  若修正需要原文以外的新資訊，那就不是修正，退回「需要補一份來源」。
- **待選事實不能直接生成**：回饋說「你們漏了 X」，
  系統只能產出**待查清單**（「民眾反映 X，事實庫未涵蓋，請提供來源文件」）。
  真正的候選事實仍必須從匯入的原文抽取。

#### AI 這一關做的是分流與初判，不是抽取

- **分流**：缺事實／既有事實有誤／不需處理／看不懂
- **科學性初判**：民眾的說法本身站不站得住。
  民眾說錯時，問題往往在「答案講得不夠清楚」而非事實有誤——要分開
- **權責初判**：涉及哪個部會、現有事實的標的對不對

#### Word 檔怎麼吃

沿用既有 `sources` 管線（新增 `source_type = 'feedback'`），
但不要試圖理解任意 Word。回饋通常是表格（一列一筆：問題／系統回答／民眾意見），
naive 文字抽取會把列的分組弄丟。

與事實包同樣「寬進嚴審」：定義推薦版面（表格固定欄位，或一則一個標題），
同時接受 csv／json，逐列可跳過。
docx 是 zip + XML，要特別解 `w:tbl` 保留列結構。

#### 結構草案

```
feedback_items
  source_id / source_version_id
  raw_text            民眾原話，永遠保留
  question            民眾問的
  system_answer       系統當時的回答（若有）
  claimed_issue       民眾認為哪裡不對
  matched_fact_id     對應到哪一條正式事實
  triage              new_fact | correction | no_action | unclear
  ai_review jsonb     科學性／權責的判定與理由
  candidate_fact_id   產出的候選事實（若有）
```

#### 接回既有事實

新候選事實帶 `parent_fact_id` 指向要修的正式事實，status 維持待審核，
審過走既有的 `revise_knowledge_fact` 自動 supersede。核定路徑不用改。

#### 量的問題

同一個誤解會被反映數十次。介面必須**按事實聚合**
（「這條事實有 12 則回饋反映同一件事」），不是逐筆待審。
不用即時，直接排進既有的 `processing_jobs` 批次跑。

#### 回饋不可信

可能是惡意的或帶議程的。設計上必須保證回饋
**永遠只能變成「請人看一下」，不能自動變成事實**。
與 §25「AI 結果不得直接成為正式知識」同一個道理。

### 7. 三個功能的共用前置：`candidate_facts.origin`

項目 4（人工改稿）、項目 6（民眾回饋）都會產生「非抽取來源的候選事實」。
`candidate_facts` 需要 `origin`：`extraction | feedback | human_edit`。
審核者必須知道這條是哪來的，判斷標準不同。
三個功能共用同一條路，不要各做一套。

**另**：請下游搜尋服務在回饋時附上它引用過的 `public_id`。
有這個鍵，`matched_fact_id` 就是確定的，不必靠內容比對去猜——
這是項目 5 與項目 6 合在一起才拿得到的好處，讓迴圈在資料上真的閉起來。

### 3. 匯出待選事實包（供其他 LLM 處理）

**來源**：使用者回饋（Phase 4 驗證後）　**完成於**：Phase 8

`/export` 可下載待審核候選事實包（JSON），包內自帶：

- **欄位說明**：每個欄位的意義、允許值、可否修改。
  `id`、`source_quote`、`source_paragraph_id`、`source_title`、`source_url`
  標記為不可修改
- **校正目標**（三項，各附具體檢查項目）：
  - 不聳動：不得放大風險、不得使用煽動字眼、保留原文的不確定性
  - 部會權責正確：食品標示與添加物屬衛福部食藥署、農產品產地與農藥殘留屬農業部、
    污染與排放屬環境部、職場暴露屬勞動部職安署；不確定就標記為待確認而非猜測
  - 科學正確性：數值、單位、劑量、暴露途徑、族群不得改動；
    相關性不得寫成因果關係；危害與風險不得混用
- **回填格式**：範例 JSON 與規則（保留 `id`、verdict 允許值、
  不得新增匯出包以外的事實）
- 匯出範圍：依目前篩選條件或指定來源文件
- **回填流程**：貼上或上傳 JSON → 比對 `id` → 檢查不可修改欄位有無被動過
  → 重新執行 `checkFactQuality` → 寫回候選事實並**維持待審核**，
  同時寫一筆 `external_correction` 審核紀錄。回填永遠不會直接核定。

實作：`supabase/functions/_shared/pack.ts`、`app/api/export/route.ts`、
`app/export/actions.ts`、`components/export/pack-import.tsx`、
`supabase/migrations/20260731000010_external_correction.sql`
